## 一、这个系统是做什么的

Daily Intelligence 是给一个长期持仓的个人投资者用的每日财经情报系统。它不做通用的财经新闻汇总，而是围绕这个人的持仓、投资框架和关心的地缘话题来收集信息、写报告、回答追问。

它和一般新闻聚合的区别：

- 报告回答的不是"市场发生了什么"，而是"这件事对我的持仓意味着什么"。
- 系统记得用户过去的判断和关注点，不是每次从零开始。
- 用户可以通过 Telegram 用自然语言改监控范围、追问细节。

几条一直坚持的原则：

- **独立运行。** 不和 Hermes Agent 共用数据库、Telegram bot 和调度器。所有 API key 只从 `~/Daily_Intelligence/.env` 读取，不去借 `~/.hermes/.env`。
- **可选部分失败不影响主流程。** 知识库、社交舆情、某个新闻源拿不到，就跳过，报告照常出。
- **花钱有数。** 每次调用模型或付费搜索都知道大概多少钱；不需要推理能力的地方不用贵模型。
- **留下痕迹。** 每次运行做了什么决定、用了多少额度、模型用了多少 token，都写进日志或存档。
- **报告要诚实。** 找到了原因就写原因和来源；没找到就写"没找到"，并说明查过哪些来源；不拿"情绪驱动"之类的说法去填空。

## 二、整体流程

### 2.1 每日两次的报告

```
定时触发（launchd）
  AM：美东 08:30（开盘前简报）
  PM：美东 20:10（夜盘收市速报，盘后交易结束后 10 分钟）
      │
      ▼
检查：今天是不是 NYSE 交易日 → 有没有别的实例在跑（文件锁）→ 这一档报告是不是已经写过
      │
      ▼
拉价格：算出当日涨跌、盘前或盘后变动、3 日和 5 日累计涨跌，标出异动
      │
      ▼
免费情报收集（Pass 0，不调用模型，不花钱）
  对每只个股：Finnhub 公司新闻 + 按公司名查的 Google News + 7 个 RSS 源 + Guardian + SEC 8-K + Yahoo 按个股新闻（yfinance）
  按公司名/代码把新闻归到对应的股票下，去重，记下每个来源查到几条
      │
      ▼
没有任何异动、没有任何个股新闻、也没有命中关注的地缘话题 → 今天不出报告，直接结束
      │
      ▼
补充背景：知识库（MemPalace + Obsidian）、Sonar 宏观简报、社交舆情、FRED 流动性
      │
      ▼
深挖（Pass 1，由代码按规则决定，不用模型）
  异动股（最多 5 只）+ 宏观话题（最多 3 个）+ 安静日选中的个股（最多 5 只），抓取文章正文（Tavily）
  定时 AM 最多 13 个额度，定时 PM 用当天剩余的全部额度；手动运行按报告自身限额单独记账
      │
      ▼
写报告（Pass 2，gpt-6-luna，推理强度 xhigh）
      │
      ▼
附带步骤：抽取 SAS 候选证据；PM 档核对当天 AM 的预判
      │
      ▼
输出：写进 Obsidian 月度报告，发邮件，发 Telegram，另发一条运行状态消息
```

### 2.2 Telegram 追问

```
用户在 Telegram 发消息 → 机器人先回"收到，处理中..."
      │
      ▼
第 1 步：用 gemma 判断这是什么指令（改监控清单 / 查状态 / 强制运行 / 追问）
      │
      ├─ 改监控清单：直接改 watchlist.md
      ├─ 查状态：返回当前配置和系统状态
      └─ 追问：
           第 2 步：拉实时价格和最近新闻（yfinance，失败时用 Finnhub）
           第 3 步：用 Parallel.ai 搜索并抓取原文（失败时用 Sonar，再失败用 Exa）
           第 4 步：gpt-5.6-luna 结合持仓和投资框架回答（失败时用 grok-4.5）
           回答记进 Obsidian 月度报告的"追问"小节
```

## 三、知识从哪里来

系统用两层知识：Obsidian 里人能直接读、能直接改的文档，以及 MemPalace 里用来做语义搜索的向量索引。（早期还有第三层"知识图谱"，2026-06-12 下线，原因见文末演进简表。）

### 3.1 Obsidian 文档

| 文件 | 内容 | 谁来写 |
|---|---|---|
| `Hermes/Daily Intelligence/watchlist.md` | 监控清单：股票、商品、汇率、地缘关键词、异动阈值、收件人、公司别名 | 用户手改，或 Telegram 指令改 |
| `Hermes/Daily Intelligence/Daily Reports/Daily_Intel_report_YYYYMM.md` | 每月的报告和追问记录 | 系统追加 |
| `Hermes/Daily Intelligence/Daily Reports/Daily_Intel_context_YYYYMM.md` | 每次报告用到的原始材料摘要（Context Log） | 系统追加 |
| `Hermes/Daily Intelligence/Layer_A_Prompt.md` | 写报告时的系统提示词：投资风格、资产结构逻辑、分析原则 | 用户维护 |
| `Hermes/Daily Intelligence/预判校准记录.md` | PM 核对 AM 预判后沉淀的教训 | 系统追加 |
| `Hermes/Daily Intelligence/SAS候选证据日志.md` | 报告里发现的、可能影响 SAS 评分的证据 | 系统追加 |
| `Finance/portfolio_report_latest.md` | 最新持仓快照 | 持仓 agent 覆盖更新 |
| `Finance/Investment Operating Manual v1.0.md` | 完整的投资决策框架（能力边界、加减仓标准、SAS 方法） | 用户维护 |
| `Finance/金融资产信息.md` | 投资框架的早期版本，Telegram 追问仍在用 | 用户维护 |

### 3.2 MemPalace

通过本机的 bridge 服务（`http://localhost:8765`）做语义搜索，回答"我之前对这件事怎么看"。

- 每份报告写完后，存一条当天当档的记录（wing=paperview，room=finance）。
- 写报告前、回答追问前，会查一下相关的历史内容（finance 和 hermes 两个 room）。
- 查不到或服务没开，就跳过，不影响报告。

## 四、监控清单（watchlist.md）

这是系统唯一的配置入口，改完下次运行就生效。现在的格式：

```markdown
## 实体别名
SPCX: SpaceX

## 个股与基金
INTC, NVDA, ORCL, PLTR, QCOM, TSLA, SPCX, AMKR, AAOI, TSM, ASML, QQQM, VOO, EWJ, SGOL

## 商品期货
GC=F, CL=F, ^TNX

## 汇率
USDCNY=X, USDJPY=X, DX-Y.NYB

## 地缘政治关键词
US-Iran: Iran, nuclear, Strait of Hormuz, Middle East, IRGC
China-Taiwan: Taiwan, strait, PLA, cross-strait, TSMC, chips
...

## 异动阈值
stock_pct: 3.0
commodity_pct: 2.0
fx_pct: 1.0
tnx_bps: 10

## 收件人
someone@example.com
```

几点说明：

- **实体别名**（可选）：写公司的常用名，一行一个股票，比如 `INTC: Intel, 英特尔`。系统用它来判断一条新闻是不是在说这家公司，也用它拼搜索词。没写的，系统会用 Finnhub 查到的公司正式名称，并缓存在 `entity_alias_cache.json`。正式名称有时不自然（SpaceX 会变成 "Space Exploration Technologies"），这种情况手写一个别名就好。这一节放在最前面。
- **收件人**一行一个邮箱。
- **Telegram 指令**可以改清单：`加 MSFT` / `删 INTC`（个股）、`加关键词 US-Iran blockade`（地缘关键词）、`加收件人 x@x.com`。改的时候只动对应那一节，其他各节原样保留；写回文件是先写临时文件再整体替换，不会写出半个文件。

## 五、报告是怎么生成的

### 5.1 价格

价格用 yfinance 拉，必须在宿主机上跑（容器里连不上 Yahoo）。AM 和 PM 用的基准不一样：

| 档 | 报告里的"价格" | 涨跌怎么算 | 什么算异动 |
|---|---|---|---|
| AM | 开盘前最新成交价 | 对比昨天收盘 | 盘前涨跌超过阈值 |
| PM | 今天收盘价 | 对比昨天收盘 | 日内或盘后涨跌超过阈值 |

另外算两个多日指标：个股 3 个交易日累计涨跌 ≥15%，或 5 个交易日 ≥20%，也算"需要解释的变动"。这是为了抓住"前几天大涨、今天已经平静"的情况（INTC 在 2026-09 就是这样被漏掉的）。商品、汇率和指数 ETF 不参与这项。

几个处理细节：

- **PM 的今日收盘价取自分钟线，不取日线。** Yahoo 的日线在晚上 8 点常常还没更新当天，曾经导致整张表显示"涨跌 0.00%"。分钟线也没有今天数据的股票，直接从价格表里去掉，并在提示词里告诉模型"这几只的价格拿不到，不许编"。
- **yfinance 偶尔会瞬间失败，**把正常的股票报成"可能已退市"。系统会再拉一次，只把第一次缺、第二次拿到的数补回去；拉取期间压低 yfinance 自己的报错日志，免得触发外部巡检误报。
- **单只股票拉不到时，用 Finnhub 补。** Finnhub 免费档没有盘前盘后数据，也没有商品和汇率。

### 5.2 免费情报收集（Pass 0）

代码在 `intel_pass0.py` 和 `intel_collect.py`，不调用任何模型，也不花钱。

**收集范围**：监控清单里的个股，不包括 QQQM、VOO、EWJ、SGOL 这四个指数或防御型 ETF。

**六个来源：**

| 来源 | 怎么用 |
|---|---|
| Finnhub 公司新闻 | 每只股票一次请求，拿全量标题和摘要 |
| Google News RSS | 用公司名查 `"公司名" stock`，拿标题、来源网站和时间。每次请求之间至少隔 1 秒。它给的链接打不开原文，只当线索用 |
| 7 个 RSS 源 | FT、CNBC、MarketWatch、Foreign Policy、Seeking Alpha、Reuters（经 Google News）、Digitimes |
| Guardian API | 国际、财经、政治新闻 |
| SEC 8-K | 每只股票查收集窗口内提交的 8-K。条目写明公司公告和 Item 编号，链接是 SEC 索引页，不抓附件正文。找不到 CIK 或请求失败只记在这只股票的覆盖里 |
| Yahoo 按个股新闻 | 用 `yfinance.Ticker(t).get_news(count=20)`，取原文地址（canonical URL）和出版方；标题或摘要要提到这家公司才收录。链接可被深挖直接选用。和已有标题重复的并到同一条。回放时跳过。覆盖字段仍叫 `yahoo_rss`。原来的 `feeds.finance.yahoo.com` RSS 地址从 2026-09-24 上线起就在本机返回 404/429，一条也没取到过（issue #111） |

NYT、BBC、Al Jazeera、AP、WSJ 五个综合新闻源在 2026-09-23 停用了。实测它们占新闻总量的 57%，但和持仓、科技、宏观相关的只有一成左右，而且把真正有用的新闻挤掉了。地址都还留在代码里（`RSS_FEEDS_DISABLED`），需要时可以恢复。

**时间范围**：AM 看过去 36 小时，PM 看过去 24 小时。触发 3 日或 5 日累计阈值的股票，往前推到那段涨跌开始之前。8-K 和 Yahoo 用同一窗口。回放能按提交日期重建 8-K；Yahoo 和共享 RSS 一样跳过。

**怎么归类**：看新闻标题和摘要里有没有这家公司的名字或代码。英文名按完整单词匹配（Intel 不会匹配到 intelligence），短名字区分大小写（Arm 不会匹配 arm），中文名单独处理。归不到任何一家公司的新闻，如果提到了关注的地缘话题，就放进"宏观"那一栏。

**每只股票记下这些东西：**

- 价格变动；
- 每个来源查到几条、有没有出错（这叫"覆盖记录"）；
- 去重后的新闻条目；如果和上一次报告里的某条标题相同，标成"此前已报道"；
- 后面深挖抓到的正文。

收集这一步如果整体出错，系统会生成一份只带错误说明的空快照，报告照常往下走。

### 5.3 深挖（Pass 1）

代码在 `intel_deepen.py`。选股、选链接和额度由代码决定，不新增模型调用。分三层处理：

1. **异动股**：当天异动或达到多日阈值的个股，按涨跌强度最多选 5 只；每只最多 2 条标题匹配、落地域名不同的直链。Finnhub 跳转只解析目标地址，不下载网页；没有直链才搜 `Why is {公司名} stock up` 或 down。
2. **宏观**：按命中量最多选 3 个话题，每个话题最多 3 条未报道过的不同域名直链；排除 `news.google.com`、`ft.com`、`wsj.com`、`barrons.com`、`foreignpolicy.com`、`marketwatch.com`。缺 `macro_digest` 时先把新字典挂回快照，再写正文。
3. **安静个股**：排除指数与防御型 ETF，最多 5 只。先看接近多日阈值（3 日 ≥8% 或 5 日 ≥9%），再看新 8-K，最后看新闻量异常。新闻量异常须有至少 5 份同档历史快照，再比较未报道条数 ≥8 且 ≥最近 10 份同档中位数的两倍。每只最多 3 条直链；接近阈值时可保留此前已报道的条目，由已抓正文 URL 去重避免重复付费。无直链才搜索 `"{公司名} {ticker} news"`。

最近 6 份情报快照中，个股或宏观 `fulltext` 已抓过的 URL，本次不再 Extract；比较时去掉 fragment 和 `utm_*` 参数。历史读取失败时本次照常运行。搜索结果若有日期且早于该标的发表窗口起点 7 天以上，就丢弃；无日期结果排在有日期结果之后，且不进入补齐轮。Yahoo 链接在同一标的有其他域名可选时排后。

额度仍是每天 25cr，定时 AM 最多 13cr、PM 用当日剩余；手动 AM 13cr、PM 12cr 单独记账，不挤占定时额度。每次最多搜索 5 次。Extract 每批最多 20 URL，按每批 `ceil(URL 数/5)` 计费；按 URL 所属标的或话题及标题关键词生成 query，同层小组可合批以减少零头。每篇取最多 3 个 chunk、截到 2000 字。Yahoo 导航先清理；正文不足 300 字、样板噪声超过 35%，或命中已标定的付费墙/版权页特征，就不写入 `fulltext`。快照和状态消息记录 `extract_dedup_skipped` 与 `extract_rejected_count`；`deepen_status` 用不重复的状态片段拼接。

2026-09-25 PM 的 20 篇旧正文离线标定是 11 篇通过、9 篇拒绝；SPCX 的 Yahoo NASA 合同页面清掉导航后，保留了有实质信息的合同段落。四份 09-24/25 快照的 mock 模拟显示分组 Extract 相比相同 URL 全局打包每档增加 0–1cr；这是离线评估，不是合并后的生产用量。每只标的的链接数未扩大，仍由 #114 决定。

深挖结果回填情报快照，存到 `archives/YYYYMM/YYYY-MM-DD-{am|pm}-intel-snapshot.json`。来源或深挖失败只记覆盖信息，报告仍由免费材料生成。

### 5.4 背景信息

- **Sonar 宏观简报**（perplexity/sonar，约 0.005 美元一次）：AM 看过去 12 小时的隔夜动态，PM 看当天盘面和盘后风险。只搜过去一天的内容；把系统算好的价格表一起给它，冲突时以价格表为准；要求每条说法都带时间。它曾经报出与实际完全不符的油价，所以有这几条约束。
- **社交舆情**：Polymarket 预测市场赔率、Adanos 的 X（推特）讨论热度、Apify 抓取的 Reddit 情绪。后两者只查个股，异动股优先，最多 4 只，各有月度额度上限。第三方返回的文字会先清理（去掉换行等可能冒充标题的内容）再用。报告里只对正文提到的股票各附一行。
- **FRED 流动性**：银行准备金、SOFR 与逆回购利差、财政部账户余额，按《市场见顶预警指标》分成正常、观察、警戒三档。
- **知识库**：MemPalace 和 Obsidian 里与异动股相关的历史内容，合计不超过 2000 字。

### 5.5 写报告（Pass 2）

用 `openai/gpt-6-luna`，推理强度 xhigh，输出上限 32000 token。

**给模型的材料：**

- 价格表；
- 情报快照，有条数上限：
  - 异动股和抓过正文的安静股：每只最多 25 条新闻（标题、来源、时间、摘要、是否此前已报道、正文片段、覆盖记录）；
  - 其他没异动的持仓：每只最多 12 个标题，每个附不超过 120 字的摘要，没报道过的排在前面；
  - 没异动的观察股：只列名字；
  - 地缘话题：每个话题最多 8 条，总共最多 40 条；抓过正文的话题排在前面，并附正文片段；抓到正文的标的另有“本次抓到正文”提示；
- 近 5 个交易日的报告里提到这些异动股的段落，每只最多 600 字，用来避免重复讲同一件事；
- **只在有变化时才给的背景信号**：FRED 档位和上次报告不同；某只个股的仓位占比跨过 15%（只看个股，不看 QQQM 这类指数和防御型持仓；第一次运行没有上次的数据，不算跨过）；某只股票创 52 周新高或新低；
- Sonar 宏观简报、相关股票的社交舆情、知识库内容、AM 档还有最近的预判校准教训；
- 持仓和投资框架（系统提示词来自 Obsidian 的 `Layer_A_Prompt.md`，持仓和 Manual 摘要放在用户消息里）。

**写作规则：**

- **解释异动时只有三种说法。** 有直接证据，写"已知原因"并注明来源；只有线索，写"线索待核实"，单一来源的强说法标"未证实"；什么都没找到，写"未找到原因"，并说明查过哪些来源各几条。检索本身失败时写"未能完成检索"。
- **不把价格变化本身当原因。** 没有证据时不说"情绪驱动""资金推动"，也不因为没找到就断言"没有公司层面的催化"。
- **材料里没人提出的推论，不要去逐条反驳**（比如"这不代表已经拿到客户"）。只有某篇报道或市场说法确实这样讲了，才用一句话指出证据不够，同一只股票只说一次。
- **只写与今天有关的进展。** 近 3 个交易日至 7 个自然日内已报道的事件，若与当日异动、接近或达到多日阈值、当日后续报道及价格变动有关，可以完整分析；写明事件原始日期，以及发酵、兑现或重新定价与当日价格的关系。更旧或无关的旧事省略或一句带过，不复述同一事实。限售股解禁、增发、配售、指数调整等已排期供给事件在生效日前后仍要写明日期、规模和当日股价关系。
- **"持仓与观察标的"写有新事件、有异动、有已排期供给事件，或近一周事件正在发酵且伴随价格变动的股票。** 本次抓到正文且有合同、订单、监管、融资、管理层、产品交付、诉讼或指引等公司级实质事件的标的必须写到；只有近五日报告写过且没有新进展才可省略。其他标的不单独成段，不复述价格表。PM 报告只在盘后走势和日内方向相反、或盘后涨跌达到异动阈值时才提盘后。
- **仓位段只在例外时出现：** 出现了符合加仓或减仓标准的新事实（认知提升、Alpha 大幅兑现、出现更高赔率的机会），或上面那几个背景信号有变化。平时不写，也不逐只写"不构成加减仓依据"。
- 不写检索过程，不列证据缺口清单，不写"本报告仅供参考"这类话。直接输出 Markdown。
- AM 报告末尾加 2–4 条"可验证信号"，供当晚 PM 核对（见 5.8）。

**出错时怎么办：**

- **网络错误、服务端错误、限流、返回空内容：** 用同样的请求重试。
- **输出被截断**（写到上限还没写完，残缺的正文也算失败）**：** 推理强度降一档（xhigh 降到 high）再试一次；还是截断就换 `google/gemini-3.5-flash`。
- **全部失败：** 用代码把情报快照整理成一份简要报告照常发出，并在 Telegram 发告警。
- **记录：** 每次的模型用量（token 数、结束原因、实际用的推理强度、有没有换模型）记在情报快照的 `pass2` 里。

一个参考数字：2026-09-23 PM 截断修复后补跑，这一步用了约 10000 个推理 token、约 2000 个正文 token，耗时约 2.5 分钟。

**SAS 候选抽取**是另一次独立调用（gemma），只看情报快照，找出可能影响 SAS 评分的证据（内部人买入、客户验证、战略节点兑现等），写进《SAS候选证据日志》。它出错不影响报告。

### 5.6 什么时候不出报告；防重和补跑

- **不出报告：** 没有任何个股异动（含多日阈值）、没有任何个股新闻、也没有命中地缘话题的宏观新闻，这一次就不写报告，也不花钱。
- **防重：** 月度报告里已经有"日期 + 档位"的标题，就不再写。
- **补跑：** 用三个环境变量：

| 变量 | 作用 |
|---|---|
| `FINANCE_FORCE_DATE=YYYY-MM-DD` | 按指定日期跑（同时跳过交易日检查） |
| `FINANCE_FORCE_SLOT=am` 或 `pm` | 指定 AM 还是 PM |
| `FINANCE_FORCE_RUN=1` | 跳过防重检查（Telegram 的"强制运行"用的就是这个） |

### 5.7 输出和存档

| 输出 | 位置 | 说明 |
|---|---|---|
| 报告正文 | Obsidian 月度报告文件 | 按"日期 + 档位"追加，会被 MemPalace 索引 |
| Context Log | Obsidian 月度 Context 文件 | 价格表、每只股票的情报摘要和覆盖记录、Sonar 原文、搜索任务 |
| 情报快照 | `archives/YYYYMM/` 下的 JSON | 全部免费来源条目、抓到的正文、深挖记录、Pass 2 用量、给下次比较用的背景状态。不放进 Obsidian，避免网页碎片污染索引 |
| MemPalace 记录 | 每次一条 | 报告正文 |
| 邮件 | 通过 Resend 发给收件人 | |
| Telegram | 报告正文（超过 4096 字自动分段） | |
| Telegram 运行状态 | 单独一条消息 | 本次 Tavily/SerpApi 用量和剩余、各来源条数和错误、深挖结果、用了哪些模型。不进邮件和 Obsidian |

`archives/` 下还有 2026-09-23 之前的 `*-extract.md` 旧存档，已停止新写。

### 5.8 AM 预判和 PM 核对

AM 报告末尾写 2–4 条当晚能核对的具体判断（比如"WTI 收盘低于某价，就说明跌势延续"）。PM 报告写完后，系统找出当天 AM 的这几条，用 gemma 对照收盘价格、情报快照和 Sonar 逐条判断：对、错、还是无法判断，并总结出一条可以迁移的教训。

- 教训写进 Obsidian《预判校准记录》，同时在 `backups/` 下写一份本地备份，也存一份到 MemPalace。
- 之后的 AM 报告会读最近 5 条教训（直接读 Obsidian，读不到就读本地备份，不依赖 MemPalace）。
- 只有重要的结果（高把握的判断被推翻、核心逻辑得到验证、出现需要警惕的偏差）才会以"预判校验"小节附在 PM 报告后面；普通的对错不展示。
- 这一步出任何错都不影响报告。

## 六、Telegram 机器人

### 6.1 运行方式

- 用独立的 bot（@PhyCluFintel_bot），和 Hermes 的 bot 分开，避免两边抢消息。
- 由 launchd 常驻运行，用长轮询收消息，服务端每次最多等 30 秒。收到消息先回"收到，处理中..."。
- **网络不稳时怎么办：** 本机代理对 Telegram 的新连接大约有 25–30% 会瞬间失败。收消息的循环本身每半分钟就会再来一次，所以失败了就等下一轮，连续失败 30 分钟以上才记警告；发消息没有"下一轮"，所以失败会立刻重试。
- **进程管理：** 整个进程共用一个网络连接对象，连续失败 3 次或满 6 小时重建一次；运行满 24 小时自动退出，由 launchd 重新拉起（防止长时间运行后内存越涨越大）。
- **改了 `telegram_commands.py` 必须重启机器人才生效：**`launchctl kickstart -k gui/$(id -u)/com.daily-intel.finance.telegram`。

### 6.2 指令

| 发什么 | 做什么 |
|---|---|
| `加 MSFT` / `删 INTC` | 增删个股 |
| `加关键词 US-Iran blockade` / `删关键词 ...` | 增删地缘关键词 |
| `加收件人 x@x.com` / `删收件人 ...` | 增删收件人 |
| `状态` | 当前监控清单、Tavily 用量、最近的 AM/PM 报告、定时任务状态、各步用的模型 |
| `强制运行` | 跳过防重立刻跑一次报告 |
| `校准统计` | 最近一段时间 AM 预判的命中率 |
| 其他任何问题 | 走追问流程 |

指令分类由 gemma 完成（输出动作类型、要改的内容、搜索词、相关股票、用户真实意图）。

### 6.3 追问流程

1. **理解问题**（gemma，约 0.0001 美元）：生成两条互补的英文搜索词，一条从事件角度，一条从数据或技术面角度；同时找出相关持仓和框架重点。
2. **拿实时数据：** 按美东时段取盘前、盘中或盘后价格（yfinance，失败用 Finnhub），以及过去 48 小时的相关新闻。夜间和周末的价格会标明"非实时"。（IBKR 实时行情接口目前停用，代码保留。）
3. **找资料**（Parallel.ai）：搜索后抓取最多 3 篇原文，每篇最多 4000 字；财经聚合网站优先。如果 gemma 判断资料明显缺一块（价格走势、市场反应或基本面解释），再补一次搜索。系统优先用 Parallel，只有它出错或拒绝服务（欠费、认证失败）时才换成 Sonar，再不行用 Exa；本地记的 Parallel 花费估算只用来观察，不会自己把它停掉。
4. **回答**（gpt-5.6-luna，推理强度 high，上限 16000 token；失败换 grok-4.5）：以实时价格为准，结合持仓成本价、投资框架和历史记忆作答，不写寒暄开场白。持仓用的是成本价，不是持仓文件里可能已经过时的"现价"。

问答记进月度报告的"追问 日期 时间"小节。

## 八、模型和成本

### 8.1 现在用的模型

所有调用都经过 OpenRouter。每一步用哪个模型，定义在 `scripts/llm_config.py` 里，可以在项目根目录的 `llm_config.json` 里按字段覆盖，改完下次调用就生效，不用改代码。这个文件纳入 git 管理，方便查改动历史。配置写错时逐项退回默认值，并记警告日志。

| 用途 | 配置名 | 模型 | 失败时换成 | 输出上限 | 大概花费 |
|---|---|---|---|---|---|
| 写报告 | `report_pass2` | gpt-6-luna，推理 xhigh，只走 OpenAI | gemini-3.5-flash | 32000 | 未核实 |
| 抽取 SAS 候选 | `sas_candidate_extract` | gemma-4-31b-it | gemini-3.1-flash-lite | 800 | 约 0.0003 美元 |
| PM 核对 AM 预判 | `am_calibration` | gemma-4-31b-it | gemini-3.1-flash-lite | 4000 | 约 0.0005 美元 |
| 宏观简报 | `macro_brief` | perplexity/sonar | 重试一次后留空 | 1500 | 约 0.005 美元 |
| 追问：理解问题 | `tg_preprocess` | gemma-4-31b-it | gemini-3.1-flash-lite | 600 | 约 0.0001 美元 |
| 追问：判断是否补搜 | `tg_gap_detect` | gemma-4-31b-it | 不触发就跳过 | 60 | 约 0.0001 美元 |
| 追问：备用研究 | `tg_research` | perplexity/sonar | Exa | 1500 | 约 0.005 美元 |
| 追问：回答 | `tg_followup` | gpt-5.6-luna，推理 high，只走 OpenAI | grok-4.5 | 16000 | 未核实 |
| 季度 SAS 评分 | （`sas_review.py` 内） | claude-sonnet 最新版 | 无 | 4000 | 约 0.05 美元/次（按实际账单读取） |

gemma 这几步都固定走 OpenInference 这家服务商。追问第 3 步的 Parallel.ai 不是模型，按次计费（搜索每千次 5 美元，抓取每千次 1 美元），一次追问约 0.007–0.012 美元。

### 8.2 付费搜索的额度

| 服务 | 上限 | 记账文件 |
|---|---|---|
| Tavily | 每天 25 个额度（定时 AM 13，定时 PM 用剩余全部）；手动运行按报告自身限额另算 | `finance_tavily_budget.json`；手动运行记在 `finance_tavily_manual_budget.json` |
| SerpApi | 每月 250 次，Tavily 不可用时才用 | `finance_serpapi_budget.json` |
| Adanos | 每月额度 | `finance_adanos_budget.json` |
| Apify（Reddit） | 每月 60 次 | `finance_apify_budget.json` |
| Brave News | 每月 800 次（主报告已不调用） | `finance_brave_budget.json` |

额度文件都按日期或月份自动重置，写入时整体替换。

### 8.3 选模型的经验

- **用来做分类、判断的小任务，要选不带隐藏推理的模型。** deepseek-v4-flash 即使不开推理，也会在后台偷偷推理，把很小的输出预算用光、返回空内容，而且表面看不出来。在 2026-07 到 08 月先后导致语义过滤崩溃、Telegram 指令分类出错、Pass 1 截断，最后都换成了实测零隐藏推理的 gemma-4-31b-it。
- **推理模型的输出上限要连推理一起算。** 推理和正文共用上限，gpt-6-luna xhigh 在 16000 的上限下曾经把整份报告截断。
- **数据质量比模型档次重要。** 给模型原文比给摘要有用；便宜模型加好材料，常常胜过贵模型加碎片。
- **别人（或另一个模型）review 提出的问题，要用真实调用验证后再采纳。**
- **Perplexity 每次搜索另收 0.005 美元，**与 token 多少无关，sonar 和 sonar-pro 实际花费差不多。
- **OpenRouter 的模型名前加 `~`，表示"始终用该系列最新版"。**
- **通过 OpenRouter 调用的模型没有官方平台自带的工具，**比如 Grok 在这里不能搜 X。

## 九、调度和运维

### 9.1 定时任务（launchd）

```
com.daily-intel.finance.am.plist        美东 08:30   开盘前简报
com.daily-intel.finance.pm.plist        美东 20:10   夜盘收市速报，然后运行 sas_review.py
com.daily-intel.finance.telegram.plist  常驻          Telegram 机器人
```

- AM 和 PM 必须是两个独立的 plist。macOS 的 launchd 在一个 plist 里写多个时间时只认第一个，这个坑踩过。
- PM 的 plist 用 `/bin/bash -c "run_finance.py; sas_review.py"`，前一个失败不影响后一个。
- 非交易日由程序自己判断后退出（`exchange_calendars` 的 NYSE 日历）。

### 9.2 日志

```
/tmp/daily_intelligence.log    报告
/tmp/finance_telegram.log      Telegram 机器人
```

httpx 库默认会把完整请求地址写进日志，而 Telegram、Finnhub、Guardian 的密钥就在地址里。所以两个脚本都把 httpx 的日志级别调到 WARNING。以后新接入把密钥放在地址里的接口，要记得同样处理。

### 9.3 常用命令

```bash
tail -f /tmp/daily_intelligence.log
cat finance_tavily_budget.json

# 补跑某天的 PM 报告
FINANCE_FORCE_DATE=2026-05-01 FINANCE_FORCE_SLOT=pm \
HERMES_DATA=~/.hermes OBSIDIAN_PATH="$HOME/Library/Mobile Documents/iCloud~md~obsidian/Documents/Paperview" \
.venv/bin/python scripts/run_finance.py

# 只重建某天的免费情报快照，不发任何东西
.venv/bin/python scripts/intel_pass0.py --replay 2026-09-21 --slot am

# 重启 Telegram 机器人
launchctl kickstart -k gui/$(id -u)/com.daily-intel.finance.telegram
```

手动跑一次完整报告约需 2–5 分钟，用脚本调用时要把超时设长一些。被中途杀掉的进程会留下锁文件，但锁跟着进程走，不会挡住下一次运行。

## 十一、季度 SAS 复盘（sas_review.py）

SAS（Strategic Alpha Score）是投资框架里用来给个股打分的方法，关注战略演化，而不是股价波动，适合按季度更新。把它塞进每日报告既浪费钱，也会逼模型从零碎新闻里硬凑结论，所以单独做成一条流程，只在财报之后运行。

- **追踪谁：** 主动个股里仓位超过 2% 的，加入 `sas_tracked_tickers.json`，只加不减。清仓后要手动 `--exclude TICKER` 才移除，历史记录保留。
- **什么时候触发：** 从 Finnhub 财报日历找到最近一次财报，在市场开始反应后的第 3 个交易日触发。盘后发布的财报，从下一个交易日开始算。
- **财报数据必须拿到：** 这是整条流程里唯一一个拿不到就不继续的步骤。重试 3 次仍失败，就发 Telegram 告警，不做任何分析。
- **用到的材料：**
  - 财报实际数据与预期差；
  - 内部人在公开市场的买入（edgartools 读 Form 4，只算主动买入，排除期权行权、扣税、授予、赠与）；
  - 最近两期 10-K 风险因素原文（交给模型比较措辞变化）；
  - SAS 候选证据日志、新闻、搜索、持仓计算信号。

  机构持仓（13F）和期权隐含波动率试过，拿不到可靠数据，没有用。
- **打分：** claude-sonnet 对战略空间、执行力、预期差、Alpha 潜力四项各打 0–10 分并写理由，不许用股价当理由。结果追加到 `Finance/SAS_Review/{TICKER}.md`，并发邮件。
- **目前只提醒不自动跑：** `NOTIFY_ONLY = True`。自动扫描命中时只发邮件提醒，附上手动命令；手动 `--ticker` 会真的运行。每天扫描后都发一条 Telegram 摘要，说明每只股票为什么触发或没触发。同一天同一只股票不会跑两次，同时只允许一个实例运行。

```bash
.venv/bin/python scripts/sas_review.py --ticker TSLA    # 手动跑一次
.venv/bin/python scripts/sas_review.py --exclude TSLA   # 永久移出追踪
```

## 十二、已知局限和待办

- **报告内容仍需生产观察。** #111 的首次 PM 材料约 2.5 万 token，正文约 1650 字。#113 已放宽近一周相关事件、明确新抓正文里的公司级事件必须写入；SPCX NASA 合同在离线材料里有标记，但是否实际写入报告要等合并后的生产运行。
- **正文清洗与去重是启发式的。** #113 用近 6 次已抓正文 URL 去重、按对象查询、Yahoo 导航清理、300 字和 35% 样板噪声门槛。旧 20 篇样本离线通过 11 篇、拒绝 9 篇；新页面结构或不同 URL 指向同文仍可能漏判，需看运行状态中的跳过数、拒绝数和正文质量。
- **供给事件。** Pass 0 会收录窗口内的 8-K（Item 编号和索引页），但附件正文不抓，也没有按生效日提醒的日历。媒体没写、8-K 又不在窗口里的供给事件，报告仍然看不到。
- **SAS 候选抽取现在只看情报快照，** 看不到 Sonar 宏观简报。要不要加回，看命中频率再定。
- **Finnhub 跳转链接的解析是一个一个串行做的，** 曾经一次花了 76 秒，已加日志观察，暂不并行。
- **32000 的输出上限目前只有一次实测样本**（约 10000 推理 token）。推理用量如果接近 25000，就要重新评估。
- **issue #45：** Telegram 指令分类全靠模型，理论上可能把"校准统计"之类的指令误判成追问，触发付费搜索。实际中还没出现。
- **issue #104：** 正文的"交叉报道"标签几乎总判为有佐证（比对的是同一只股票自己的新闻，公司名天然重叠），却仍送给 Pass 2，和"单一来源的强说法标未证实"的规则冲突。已记录，未设计。（取代已关闭的 #47。）
- **可以做的扩展：**
  - A 股行情（腾讯接口）；
  - Serper 作为第三层搜索备用；
  - Parallel.ai 额度紧张时减少补搜；
  - IBKR 稳定后恢复为夜间和周末的实时价格来源。
